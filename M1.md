# M1 — the product works

M0 proved the risky pieces in isolation. M1 is the vertical slice: one command, from an
empty directory to a running app you can look at, with the agent's work checkpointed.

```
npx kiln my-app
```

## What is there now

| Piece | Where |
|---|---|
| CLI, single command | `src/cli.ts` |
| Daemon: session, dev server, preview proxy, history, capture | `src/daemon/` |
| Event stream over SSE | `src/daemon/server.ts` |
| UI: chat, tool timeline, preview, history, permission and question modals | `ui/` |
| Git checkpoints and restore | `src/project/history.ts` |
| Screenshot injection policy | `src/injection/policy.ts` |
| Dependency installation | `src/runtime/deps.ts` |

## Verified end to end

`npm run probe` — nine probes. The four that matter most for "is this a product":

- **`scaffold`** — an empty directory. The agent writes a Vite + React app, Kiln installs
  dependencies, Vite starts, and the preview appears with no user action.
- **`e2e`** — daemon, UI, injected client, a real turn, a git checkpoint containing only
  that turn's files, and a restore.
- **`t0`** — Alt-click an element on a Go server and the agent names `main.go:18`.
- **`image`** — the model reads a token out of a real screenshot. The visual loop works.

The rest re-verify M0: session, tools and permissions, conversation rollback, runtime
detection, transform-time provenance.

## Design decisions worth knowing

**Rollback is two independent halves.** The SDK's `resumeSessionAt` forks the
conversation; a `git reset --hard` restores the files. Each turn commits to a `kiln`
branch with the SDK prompt uuid in the commit message, which is what lets the two be
joined later. The first commit is the scaffold, so the history reads as "scaffold, then
one entry per turn".

**Screenshots are rationed.** `src/injection/policy.ts` decides whether the agent should
see the preview at all: on failure, on new console errors, when UI files changed, or when
the screen actually changed since the last capture — and then only for the first three
turns, after which it assumes the agent can already see it. A screenshot every turn
floods context and measurably degrades output. The policy is an explicit, tested module
precisely because that failure is quiet.

**The preview is a proxy, and the project is never modified.** Kiln sits in front of
whatever dev server it found, injects its client into HTML responses, and forwards
websocket upgrades so HMR survives. Alt-click in the preview to select an element; the
agent can then be told what to change by name.

**Kiln installs dependencies.** A scaffolded project has no `node_modules`, and nobody
should have to know that. Install runs before the preview comes up, and the agent is told
what happened.

**The permission gate auto-allows `mcp__kiln__`.** Kiln's own tools route through
`canUseTool` like everything else, so without that rule the user would be prompted for
every screenshot.

## Not done

- **M2 visual editor.** Provenance ids and the selection overlay exist; the property
  editor that turns "make this button red" into a structured edit does not.
- **M3 GitHub and publish.** No remote, no commits pushed upstream, no deploy targets.
  Git is local-only, on a `kiln` branch.
- **Backend parity.** Only the Claude SDK backend. ACP and opencode adapters are
  designed for, not written. Only the default model was routable in this environment, so
  `KILN_MODEL` is the escape hatch.
- **M4 Lovable parity.** No database, auth, knowledge documents, Figma import or
  templates.

## Known rough edges

- The pending-permission timeout is 10 minutes. A closed tab leaves the agent waiting
  rather than failing fast, which is deliberate but untested under real use.
- T0's hit rate is still `n=1` on one stack. M1 was the right place to widen it and that
  did not happen.
- The Go, Python and Ruby install paths are implemented but only the Node one has been
  exercised end to end.
